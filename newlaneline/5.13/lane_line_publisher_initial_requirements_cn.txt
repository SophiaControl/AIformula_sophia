Lane Line Publisher 初始修改要求整合
====================================

一、文件和版本处理要求
------------------------------------
1. 只看当前有效的新代码，不看 backup、copy、旧日期命名的文件。
   例如文件名中带有 BKUP、backup、copy、0227、0319 等明显备份或历史存档含义的文件，不作为当前修改对象。

2. 修改目标是新的 lane_line_publisher 主体逻辑。
   不要把旧版本存档中的逻辑误认为当前运行逻辑。

3. 尽量把主体逻辑集中放在 lane_line_publisher.cpp 一个文件中。
   其他类似 cubic fitter、pixel finder 这种辅助逻辑，最好不要再分散调用外部文件。
   虽然代码行数会增加，但这样便于直接阅读、检查和修改。

4. 拟合模块命名要准确。
   当前逻辑不应再叫 CubicLineFitter。
   实际应明确分成两个部分：
   - 图像坐标系一次拟合：用于下一帧 ROI 生成；
   - 车辆坐标系二次拟合：用于当前帧实际输出点云。


二、上下游接口保持要求
------------------------------------
1. ROS topic 名称和消息类型必须保持和原先代码一致，不能乱改接口。

2. 输入保持：
   - mask_image

3. 输出保持：
   - lane_lines/left
   - lane_lines/right
   - lane_lines/center

4. debug 输出尽量保持：
   - annotated_mask_image
   - contour_points/left
   - contour_points/right
   - contour_points/center

5. 下游模块仍然按照原来的 topic 接收车道线点云。
   因此，修改重点是内部检测和拟合逻辑，而不是改 topic 接口。


三、主体逻辑修改目标
------------------------------------
总体目标是把原先“逐行搜索第一个像素点”的逻辑，改成“上一帧一次拟合线引导的可变 ROI + ROI 内所有像素点参与拟合”的逻辑。

新的主体流程应为：

上一帧保存的一次拟合线
    ↓
根据一次线扩展 margin
    ↓
生成当前帧的可变 ROI
    ↓
mask ∩ ROI
    ↓
提取交集区域内所有白色像素点
    ↓
分成两条支路：
    1. 车辆坐标系二次拟合 → 当前帧实际输出点云
    2. 图像坐标系一次拟合 → 保存给下一帧生成 ROI

重点要求：
1. 不再每一行只找第一个像素点。
2. ROI 和 mask 交集中的所有有效像素点都要参与拟合。
3. 一次拟合和二次拟合职责要分开：
   - 一次拟合负责下一帧 ROI tracking；
   - 二次拟合负责当前帧最终输出。


四、ROI 生成要求
------------------------------------
1. 可变 ROI 在图像坐标系中生成。

2. 上一帧保存的是图像坐标系中的一次拟合线，推荐形式为：
   u = a*v + b

   其中：
   - u 表示图像列坐标；
   - v 表示图像行坐标。

3. 使用 u = a*v + b 的原因：
   图像中的车道线通常接近竖直方向。
   如果写成 v = a*u + b，接近竖直线时斜率容易发散。
   用 u = a*v + b 更稳定。

4. 当前帧根据上一帧一次线预测每一行的车道线位置：
   u_pred(v) = a*v + b

5. 在 u_pred(v) 左右扩展 margin，得到该侧车道线的带状 ROI：
   abs(u - u_pred(v)) <= margin(v)

6. margin 需要近处宽、远处窄。
   目的：
   - 近处允许较大的车辆姿态变化和检测误差；
   - 远处收窄，减少远端横线、斑马线和背景干扰。

7. 可使用线性变化的 margin：
   margin(v) = margin_far + (margin_near - margin_far) * (v - v_top) / (v_bottom - v_top)

   其中：
   - v_top 是有效检测区域上边界；
   - v_bottom 是图像底部；
   - margin_near 是近处较大的 ROI 半宽；
   - margin_far 是远处较小的 ROI 半宽。

8. 这个 ROI 不是固定矩形，也不是简单裁掉上半部分。
   它应该是跟随上一帧车道线方向变化的可变带状区域。


五、初始状态和丢失状态要求
------------------------------------
1. 没有上一帧一次线时，该侧进入初始化搜索。

2. 初始化搜索是按侧独立进行，不是左右两侧一起重置。
   - 左侧缺失，只初始化左侧；
   - 右侧正常，右侧继续使用 tracking ROI；
   - 右侧缺失同理。

3. 初始化搜索时：
   - 左侧只在图像左半区搜索；
   - 右侧只在图像右半区搜索；
   - 同时裁掉图像上半部分，减少天空、背景和远端噪声干扰。

4. 初始化阶段也不应使用旧的逐行第一个像素搜索。
   应该提取对应半区内所有有效 mask 像素点参与拟合。

5. 如果某一侧连续多帧点数过少，超过 lost 阈值后，该侧 stored line 失效，并重新进入该侧初始化搜索。

6. 左右两侧应分别维护状态，例如：
   - previous linear fit；
   - valid flag；
   - lost_count。


六、点数过少时的处理要求
------------------------------------
1. 点数过少时，当前帧该侧必须输出空白 point cloud。

2. 不能继续输出上一帧结果。
   否则下游会误以为当前帧仍然检测到了有效车道线。

3. 点数过少时：
   - 当前侧输出空；
   - 当前侧 lost_count 增加；
   - 不用当前帧的错误或不足数据更新 stored line；
   - 如果 lost_count 超过阈值，该侧进入初始化搜索。

4. 可以在内部短时间保留上一帧一次线，用于下一帧尝试恢复 tracking。
   但这只用于内部 ROI recovery，不代表当前帧可以输出上一帧点云。

5. 本模块不做单侧线补偿。
   如果只有一侧白线有效，另一侧无效，则：
   - 有效侧正常输出；
   - 无效侧输出空；
   - center 不生成。


七、横线、斑马线和斜率过滤要求
------------------------------------
1. 斜率/角度判断应针对 mask ∩ ROI 后得到的像素点的一次拟合结果。

2. 因为一次拟合线用于下一帧 ROI，所以它本身就有斜率，可以用于判断是否像横线。

3. 对图像坐标系一次拟合：
   u = a*v + b

   方向角可以根据方向向量计算。
   主要目的是过滤接近水平的线或大面积横向干扰。

4. 需要去掉斜率角度小于 12° 或大于 168° 的情况。
   这类情况一般对应横向线段或横线干扰。

5. 但是横线过滤的主要目标不是单独增加一个复杂的新模块，而是通过整体逻辑达到：
   - ROI 跟随上一帧左右白线；
   - ROI 远处更窄；
   - mask ∩ ROI 限制候选区域；
   - 一次拟合角度不合理时拒绝；
   - connected component 保持原有结构，并可在该结构内做必要的面积/形状过滤。

6. connected component 部分按原先代码结构保留。
   不需要完全重写成独立的新处理链。
   但需要避免大面积横线、斑马线、白色横向块直接污染拟合。


八、一次拟合更新时机要求
------------------------------------
1. stored line 不应在图像坐标系一次拟合刚成功后立刻更新。

2. 正确顺序应该是：
   - 提取 mask ∩ ROI 像素；
   - 图像坐标系一次拟合通过；
   - 水平线/角度检查通过；
   - 跳变检查通过；
   - 同一批像素点投影到 vehicle frame；
   - vehicle-frame ROI crop 后点数足够；
   - 车辆坐标系二次拟合成功；
   - 当前侧实际输出有效；
   - 然后才更新 stored line。

3. 如果二次拟合前任何关键步骤失败，该帧不应更新 stored line。

4. 这样可以避免：
   当前帧没有有效输出，但错误的一次线已经影响下一帧 ROI。


九、跳变检查要求
------------------------------------
1. 可以比较当前一次拟合线和上一帧一次拟合线的变化，用于防止 ROI 大幅跳变。

2. 但是跳变检查要宽松，因为弯道时车道线方向会明显变化。

3. 不建议只比较斜率 a。
   更适合比较一次线在图像底部和上边界的预测位置：
   - u_bottom；
   - u_top。

4. 只有当 top 和 bottom 位置变化明显异常时，才拒绝当前线。

5. 可以对 accepted 的一次线做平滑更新：
   new_line = alpha * current_line + (1 - alpha) * previous_line

6. 平滑系数不要太保守，避免弯道跟不上。


十、二次拟合和车辆坐标要求
------------------------------------
1. ROI 筛选在图像坐标系完成。

2. 实际输出的二次拟合应在车辆坐标系中完成。

3. 处理顺序是：
   - 图像中提取 ROI 内所有 mask 像素；
   - 将这些像素投影/转换到 vehicle frame；
   - 在 vehicle frame 中进行 ROI crop；
   - 对 crop 后的点进行二次拟合；
   - 输出拟合后的 lane point cloud。

4. 二次拟合形式为：
   y = c0 + c1*x + c2*x^2

5. 二次拟合用于实际输出，不能再误称为 cubic fitting。


十一、center line 生成要求
------------------------------------
1. 原先先找 center pixels，再让 left/right/center 一起进入后处理拟合的方式要取消。

2. center 不再从 mask 中单独检测。

3. center 应由左右两侧车辆坐标系二次拟合后的输出结果生成。

4. 如果 left 和 right 当前帧都有效：
   center_i = 0.5 * (left_i + right_i)

5. 如果缺任意一侧：
   - center 输出空；
   - 不根据单侧白线补 center；
   - 不使用车道宽度补偿；
   - 不沿用上一帧 center。

6. 原因：
   本模块只负责检测、坐标转换和拟合。
   缺线补偿、车道宽度估计或控制层安全策略应由后续模块处理。


十二、左右线几何一致性要求
------------------------------------
1. 生成 center 前，应检查 left/right 的几何一致性。

2. 至少需要避免以下情况：
   - 左右线交叉；
   - 左右间距明显不合理；
   - 左右间距沿 x 方向变化过大；
   - 一侧是真实白线，另一侧是横线或噪声，但仍被误判 valid；
   - 由错误左右线生成错误 center。

3. 如果几何一致性检查不通过：
   - left/right 可以各自发布；
   - center 不生成。


十三、不同场景下的目标行为
------------------------------------
1. 正常直道，两侧白线清楚：
   - left 有效；
   - right 有效；
   - center 有效；
   - center 位于左右拟合线之间。

2. 弯道：
   - ROI 应跟随上一帧白线变化；
   - 二次拟合用于表达弯道曲率；
   - 跳变检查不能过严；
   - 远处 ROI 不能过窄到截掉真实弯道白线。

3. 只有单侧白线：
   - 有线侧输出；
   - 缺线侧为空；
   - center 为空。

4. 两侧都没有白线：
   - left/right/center 都为空；
   - lost_count 增加；
   - 超过阈值后重新初始化搜索；
   - 不输出上一帧结果。

5. 前方有斑马线或横线：
   - ROI 应尽量贴合两侧车道线；
   - 远处 ROI 变窄；
   - 横向大面积白色区域不应轻易生成 left/right；
   - 如果左右线中有一侧被横线污染，center 不应生成。

6. 虚线、断线或短暂遮挡：
   - 点数足够时输出；
   - 点数不足时当前帧输出空；
   - 短时间内可用 stored line 尝试下一帧恢复；
   - 不用上一帧点云假装当前帧有效。


十四、debug 和可读性要求
------------------------------------
1. 代码中应有中文注释或中文段落标注，方便检查每个部分的作用。

2. 建议按以下模块分段标注：
   - 参数读取；
   - 状态变量；
   - mask 二值化；
   - connected component 过滤；
   - 初始化搜索；
   - tracking ROI 生成；
   - 图像坐标一次拟合；
   - 一次线角度和跳变检查；
   - 像素到车辆坐标转换；
   - vehicle-frame ROI crop；
   - 车辆坐标二次拟合；
   - stored line 更新；
   - center 生成；
   - point cloud 发布；
   - debug 输出。

3. debug 输出应尽量语义清楚：
   - contour_points/left 和 contour_points/right 最好表示当前帧有效参与二次拟合的 vehicle-frame crop 后点；
   - contour_points/center 如果 center 有效，可以发布生成后的 center points；
   - annotated_mask_image 可以显示当前提取到的 left/right ROI 像素，用于检查 ROI 是否正确覆盖白线。


十五、总体目标总结
------------------------------------
最终要实现的是：

1. 输入输出接口保持原样；
2. 不再使用逐行第一个像素点搜索；
3. 上一帧一次线生成当前帧可变 ROI；
4. ROI 内所有 mask 像素参与拟合；
5. 图像坐标一次拟合用于下一帧 ROI；
6. 车辆坐标二次拟合用于当前帧实际输出；
7. 左右两侧独立 tracking、lost 和初始化；
8. 点数过少时当前帧输出空；
9. 不做车道宽度补偿；
10. center 只由左右二次拟合后的结果生成；
11. 缺任意一侧时 center 为空；
12. 对横线、斑马线、大面积白色噪声要有防护；
13. stored line 只能在当前侧实际输出成功后更新；
14. 代码尽量集中在 lane_line_publisher.cpp，便于阅读和维护；
15. 中文注释要清楚标明每个模块的作用。
